## 1. 问题与约束

### 1.1 用户拍板必须改的两处

1. 深色统计页趋势柱现在是「中性灰 + 今日蓝」，与 `docs/UI-UX设计规范.md` §1.2「支出 = error 红、
   收入 = primary 蓝」的语义护栏不一致。
2. 环形图 10 色板偏暖橙/橄榄，浅色底有 3 色 <3:1，且不贴「小狗风」淡蓝品牌。

### 1.2 硬约束（不可越线）

| 约束 | 来源 | 对本方案的影响 |
|------|------|----------------|
| 图形 ≥3:1、文字 ≥4.5:1，浅深都要过 | `docs/UI-UX设计规范.md` §0.2 第 7 条 | 决定色值亮度窗口 |
| 支出红 / 收入蓝，**不得用红蓝做唯一选中态** | 同上 §1.2 | 高亮必须另加非颜色通道 |
| 圆角容器 16–24dp、进度条细条 3–4dp | 同上 §0.2 第 6 条 | 占比条保持 6dp、圆角 3dp 不变 |
| 不用实验 API | 同上 §0.2 第 8 条 | 只用 `drawArc` / `Stroke`，不碰 `ExperimentalMaterial3Api` |
| 唯一色板源 = `Color.kt` | 用户 m00001 | 新色值全部落在 `Color.kt` |
| 金额 Long 分、统计口径见 `StatsCalculator` | AGENTS.md 2 / 3 | 只改「怎么画」，不碰口径与排序 |
| 不加依赖、不动数据、不做破坏性迁移 | 用户 m00001 | 纯 UI 层改动：零 gradle 改动、零 Room 改动、零 schema 改动 |

### 1.3 数学窗口（为什么「一套色深浅共用」可行）

统计页**没有卡片容器**：环形图、占比条、趋势柱都直接画在 `surface` 上。

- 浅色底 `surface = #F5FAFF`，相对亮度 L = 0.9500
- 深色底 `surface = #0E1418`，相对亮度 L = 0.0100

一个颜色对浅底要 ≥3:1，则 L ≤ (0.95+0.05)/3 − 0.05 = **0.2805**；
对深底要 ≥3:1，则 L ≥ 3×(0.01+0.05) − 0.05 = **0.1224**。

→ 可行亮度窗口 **L ∈ [0.1224, 0.2805]**，宽度只有 0.158。这是「同一套 10 色同时服务深浅主题」
在数学上成立的全部根据，也解释了为什么选色必须精确控制亮度、不能凭手感。

## 2. 决定 1：趋势柱语义色

### 2.1 为什么不直接把柱色绑到 `colorScheme.error / primary`

`TrendChart.kt:326-327` 现在取的就是 `colorScheme.error` / `colorScheme.primary`。看着「语义正确」，问题是：

- 浅色 `LightColors.primary = #0B5A8C` 是**深蓝**，放在两根并排的柱子上，蓝柱几乎黑掉，与红柱的观感重量严重失衡；
- 深色 `DarkColors.primary = #79C9FC` 是**品牌容器色**，对深底 10.22:1，一根柱亮到发光，
  整页「一屏一个蓝时刻」（§1.1）被柱图吃掉；
- `primary/error` 是**文字/按钮角色**，改它们会牵动全 App 的按钮、金额文字、选中态——用错了抽象层级。

### 2.2 方案：新增 4 个图表柱专用色（不动 primary/error 本体）

在 `Color.kt` 追加（**放在文件末尾，LightPrimary/LightError 之后**，见 §6.1）：

```kotlin
/** 趋势柱（图表填充，非文字）。支出偏红、收入偏蓝；浅深各一档，靠 Oklab 亮度阶梯拉开两柱灰度差 */
val ChartExpenseBarLight = Color(0xFFB9504B)   // Oklab L 0.565
val ChartIncomeBarLight  = Color(0xFF528AB9)   // Oklab L 0.615
val ChartExpenseBarDark  = Color(0xFFC05A52)
val ChartIncomeBarDark   = Color(0xFF76A6D2)
```

对外只暴露一个按主题取色的入口（放 `ui/theme`，纯函数可单测）：

```kotlin
data class ChartBarColors(val expense: Color, val income: Color)
@Composable fun ledgerChartBarColors(): ChartBarColors =
    chartBarColorsFor(dark = isSystemInDarkTheme())

internal fun chartBarColorsFor(dark: Boolean): ChartBarColors =
    if (dark) ChartBarColors(ChartExpenseBarDark, ChartIncomeBarDark)
    else ChartBarColors(ChartExpenseBarLight, ChartIncomeBarLight)
```

> **不能**用自定义 `ColorScheme` 承载这 4 个新色：那要造一整套 colorScheme，侵入面太大。
> `isSystemInDarkTheme()` 与 `Theme.kt` 的 `darkTheme` 参数同源（`Theme.kt:18-20`）；
> 若将来 `LedgerTheme` 支持强制浅色，这里要改成读 `LocalLedgerDarkTheme`（见 §8 U4）。

### 2.3 逐色对比度复核（门槛：图形/填充 ≥3:1）

| 色值 | 角色 | 浅底 #F5FAFF | 深底 #0E1418 | 浅容器 #E9F2FB | 深容器 #1A232A | 浅段头 #DCE7F2 | 深段头 #3B4A55 |
|------|------|--------------|--------------|----------------|----------------|----------------|----------------|
| `#B9504B` | 浅·支出 | **4.64** | 3.81 | 4.30 | 3.27 | 3.89 | 1.88 |
| `#528AB9` | 浅·收入 | **3.51** | 5.03 | 3.26 | 4.32 | 2.94 | 2.48 |
| `#C05A52` | 深·支出 | 4.14 | **4.26** | 3.85 | 3.66 | 3.47 | 2.10 |
| `#76A6D2` | 深·收入 | 2.45 | **7.20** | 2.28 | 6.19 | 2.05 | 3.55 |

**实际生效的只有加粗两列**：趋势柱永远画在 `surface` 上，最小值 **3.51:1**（浅色收入柱）。
其余列是「将来谁把柱图挪进卡片」的预留复核——若真挪进 `surfaceVariant` 段头
（`ReportsScreen.kt:349-373` 的 `SectionHeader` 就是 `surfaceVariant` 通栏），
浅色收入柱只剩 2.48:1，**届时不达标**，见 §8 U1。

### 2.4 两柱之间的可区分性（不靠颜色也能分）

| 主题 | 支出柱亮度 | 收入柱亮度 | 亮度比 | OKLab ΔE |
|------|-----------|-----------|--------|----------|
| 浅色 | 0.166 (#B9504B) | 0.235 (#528AB9) | **1.42×** | **22.2** |
| 深色 | 0.191 (#C05A52) | 0.358 (#76A6D2) | **1.87×** | **23.4** |

两柱并排且间距仅 `Arrangement.spacedBy(1.dp)`（`TrendChart.kt:359`），1.42× 的亮度差让灰度打印 /
黑白截图下也能分辨左右。**这是「支出深一档、收入浅一档」的设计理由**——不是审美，是冗余信道。

通道守门（沿用 `LedgerPaletteTest.kt:140-145` 的判据）：支出柱 R>B（`#B9504B` 0xB9>0x4B ✔、
`#C05A52` 0xC0>0x52 ✔），收入柱 B>R（`#528AB9` 0xB9>0x52 ✔、`#76A6D2` 0xD2>0x76 ✔）。

### 2.5 与既有 error/primary 的关系（会不会「看起来像两套红蓝」）

| 比较 | OKLab ΔE | 结论 |
|------|----------|------|
| 浅色支出柱 `#B9504B` vs `LightColors.error #B3261E` | 7.7 | 同族不同档；柱是填充、文字是文字，不并排出现 |
| 深色支出柱 `#C05A52` vs `DarkColors.error #FFB4AB` | 25.1 | 明显不同档，避免「浅粉柱」在深底过亮 |
| 浅色收入柱 `#528AB9` vs 品牌容器 `#79C9FC` | 19.0 | 分得开；柱不抢品牌蓝的「容器」身份 |
| 深色收入柱 `#76A6D2` vs `#79C9FC` | 10.0（对比 2.03:1） | 相邻但可辨；深色柱是填充，品牌蓝仍只在容器/文字出现 |
| 浅色支出柱 vs 新分类色 slot6 `#AB5334` | 4.1 | **最近邻**，见下 |

**已知代价**：支出柱与新分类色 slot6 的 ΔE 只有 4.1、收入柱与 slot1 只有 3.2。它们在页面上不会并排
（趋势图与环形图中间隔着段头「分类占比」），且柱有图例、环形图有占比条，故判定**不构成混淆**。
但这是「需要人眼最终确认」的点，见 §8 U3。

### 2.6 今日 / 选中高亮：怎么和普通柱区分

现状：`TrendChart.kt:329` `val highlight = colorScheme.primary.copy(alpha = 0.10f)`，
`TrendChart.kt:354` 用它在选中日整格铺底色。

**决定 D3：alpha 保持 0.10f，不加码。** 理由（复核数字）：

| overlay | 合成底色 | vs 底 | 其上·支出柱 | 其上·收入柱 |
|---------|----------|-------|-------------|-------------|
| 浅 0.10 | `#DEEAF4` | 1.16 | **3.98** | **3.02** |
| 浅 0.12 | `#D9E7F1` | 1.20 | 3.86 | **2.92 ✗** |
| 浅 0.14 | `#D4E4EF` | 1.24 | 3.74 | **2.83 ✗** |
| 深 0.10 | `#19262F` | 1.20 | **3.55** | **6.00** |
| 深 0.12 | `#1B2A33` | 1.26 | 3.38 | 5.72 |
| 深 0.14 | `#1D2D38` | 1.31 | 3.25 | 5.49 |

→ 浅色主题是瓶颈：**alpha 一旦 >0.10，收入柱在选中格上就掉到 3:1 以下**。
§10.1 / 清单 E-6 建议的「0.10f→0.14f」**在浅色主题下会破坏 3:1，建议不采纳**（见 §8 U2）。

**非颜色的选中通道（现状已有，补文档即可）**：
- 选中格整格铺底色（形状/位置通道，不依赖红蓝）；
- 选中日柱高 + 气泡文字（`DAY_TOOLTIP_TEST_TAG`），气泡里有日期与金额（数字通道）；
- 底部「支出/收入」图例 + 单位（`TrendLegend`，`TrendChart.kt:585-600`）。

**明确不做**：不给选中格加 1dp 描边。候选描边色在浅色主题下要么太弱
（`outlineVariant #C2D3E2` 对底仅 1.46:1），要么太重（`onSurfaceVariant #41566A` 对底 7.24:1，
一个深色方框会盖过柱图本身，偏离「小狗风」轻量调性）。若实机看下来深色下 0.10 仍不明显，
可按 §8 U2 只对深色加描边（候选 `#C7D6E3` 对 `#0E1418` 有 12.51:1）。

### 3.2 旧板为什么要换（对照数字）

| 指标 | 旧 10 色 | 新 10 色 |
|------|----------|----------|

### 3.3 相邻可区分性：靠「亮度奇偶阶梯 + 色相间隔」两条腿

搜参过程（供复查，全部为实测）：

- **失败 A**：按亮度+彩度联合扫描，最优解落在 Oklab L=0.640，贴死 0.2805 上限无余量，
  且出现 `#F13F61` 荧光红、`#A665EF` 艳紫——调性跑偏。
- **失败 B**：随机搜参（要求相邻 ΔE≥8 且两侧对比≥3.2）跑 60000 次**无一通过** →
  在「亮度可用区间只有 0.158」的前提下，单靠色相差撑不起 ΔE≥8。
- **失败 C**：手定彩度档（相邻高低错开）最小 ΔE 只有 5.7，卡在灰青 `#6A8A8A` 与松绿 `#528F6F`。
- **成功做法**：让**亮度在相邻槽位之间交替**（偶数槽 Oklab L=0.545、奇数槽 0.605），
  色相均匀铺开，彩度按色相调整到不过艳。亮度阶梯贡献约 6 ΔE、色相贡献约 7 ΔE，合起来最小 **8.4**。

**代价（必须写明）**：为了让 10 色两两都过 3:1，色相不得不铺满一圈（含橙/绿/紫），
这偏离了「清一色淡蓝」。本方案的取舍是：**品牌调性由容器与主按钮（`#79C9FC` / `#0B5A8C`）承担，
不靠分类色承担**；分类色只保证「对得上号、分得开」。这与 `CategoryDonut.kt:86` 既有注释
「颜色只用来对号，具体数字一律看下面的排行」的设计意图一致。

### 3.4 色觉模拟（Machado 2009 线性矩阵，严重度 1.0）

| 视觉类型 | 相邻最小 ΔE | 相对正常 | 浅/深最差对比 |
|----------|-------------|----------|---------------|
| 正常 | 8.4 | 100% | 3.47 |
| deuteranopia（绿色盲） | 5.7 | 67% | 3.43 |
| **protanopia（红色盲）** | **3.6** | **43%** | **2.95** |
| tritanopia（蓝色盲） | 5.4 | 65% | 3.35 |

- 对比度在红绿色盲下基本不掉（3.43 / 2.95），说明**亮度阶梯起了作用**——这正是选「亮度交替」
  而非「纯色相变化」的主要动机。
- **红色盲下相邻 ΔE 掉到 3.6，这是本方案明确的、无法在 10 色约束下消除的代价**。
  缓解靠非颜色通道：`DONUT_DESCRIPTION` / `donutDescription`（`CategoryDonut.kt:80-82`，读屏文案）、
  点扇区弹 `DonutTooltip`（分类名 + 金额 + 占比）、正下方「支出排行」（名称 + 百分比 + 金额 + 条长）。

### 3.5 稳定映射：categoryId → 槽位

**现状缺陷**：`CategoryDonut.kt:102` 是 `donutColorAt(index) = DONUT_COLORS[index % size]`，
`index` 来自「金额降序」的位置（`StatsCalculator.categoryBreakdown` 按 `sortedByDescending { it.amountCents }`）。
→ 这个月「餐饮」排第一是 `#B4643C`，下个月掉到第三就变 `#E0B457`。**同一分类跨月跳色**，
用户建立不起来「颜色 = 分类」的肌肉记忆。

**新规则（两步，都是纯函数，可单测）**：

```kotlin
private const val PALETTE_SIZE = 10
private const val SLOT_STRIDE = 7      // gcd(7, 10) = 1 → 10 个槽位双射铺满
private const val SLOT_OFFSET = 3      // 让最常见的 1 号分类不总落在槽位 0

/** 首选槽位：把连续 categoryId 打散到不相邻的色相上 */
internal fun preferredCategorySlot(categoryId: Long): Int =
    (((categoryId * SLOT_STRIDE + SLOT_OFFSET) % PALETTE_SIZE + PALETTE_SIZE) % PALETTE_SIZE).toInt()

/**
 * 稳定取色：同一 categoryId 在任何月份、任何排序下都落在同一槽位。
 * 仅当同月出现槽位冲突（分类数 > 10 或哈希撞车）时，才在本月内做一次确定性避让。
 */
internal fun categoryColors(rows: List<CategoryBreakdownRow>): Map<Long, Color>
```

**为什么步长取 7**：`gcd(7, 10) = 1` → 映射是 10 上的**双射**，10 个分类恰好铺满 10 个槽位无浪费；
同时把「ID 连续」打散成「槽位跳跃」（id 1→8、2→1、3→4…），避免相邻 ID 落到相邻色相上。

**为什么不用「按分类名哈希」**：分类名是用户可改文案，改名即换色；且多语言下同一 ID 会跳色。**否决**。

**冲突处理（同月内确定性避让）**：按 `rows` 既有降序依次处理，若首选槽位已被占用，
则从首选槽位向后线性探测第一个空槽（`slot = (preferred + k) % 10`，k 递增）。
规则确定、与调用顺序一致，**没有随机性**。

**两个不变量（必须由测试守住）**：
1. **同月唯一**：同一份 `rows` 里不会有两个分类拿到同一槽位。
2. **图条同色**：环形图与「支出排行」占比条**调用同一个 `categoryColors(rows)`**，传同一份 `state.breakdown`。
   只要两边都从这一个 Map 取色，就不可能出现「图上一个色、条上另一个色」。

**代价（写明）**：分类数 >10 时，避让会使「第 11 个分类」的颜色取决于当月其他分类，跨月可能漂移。
这是**有界代价**（只有 >10 个分类的月份才发生），且不变量 2 仍成立。常规 5–10 个一级分类不会触发。

### 3.6 是否保留 2dp 色缝：保留，规格定为 1.5dp

**为什么必须保留**：WCAG 1.4.11 允许「用相邻颜色对比替代边界对比」，但本 10 色**做不到**。
全 10 色两两对比最低三对：`#157F84` / `#697832` = 1.02、`#9450A3` / `#AB5334` = 1.02、
`#7F72CE` / `#A0794C` = 1.03。**1.02:1 相当于「没有边界」**——两个扇区直接相邻时，
即使色觉正常的用户在某些配对上也会分不清界在哪。所以缝是必须的，且必须由背景色提供。

**缝的对比度（缝色 = `surface`）**：

| 色值 | 缝对浅表面 #F5FAFF | 缝对深表面 #0E1418 |
|------|--------------------|--------------------|
| `#157F84` | 4.54 | 3.89 |
| `#268CB8` | 3.62 | 4.88 |
| `#2C6FC4` | 4.79 | 3.69 |
| `#7F72CE` | 3.85 | 4.59 |
| `#9450A3` | 5.08 | 3.48 |
| `#D74664` | 4.04 | 4.37 |
| `#AB5334` | 4.98 | 3.55 |
| `#A0794C` | 3.75 | 4.71 |
| `#697832` | 4.62 | 3.83 |
| `#42982D` | 3.47 | 5.09 |

→ 缝与每一块扇区的对比 **3.47–5.09:1，全部 ≥3:1**。也就是说：不靠扇区之间的色差，
靠「扇区 vs 缝」的对比就已经满足 3:1 边界要求。这是保留缝的完整论证。

**规格：1.5dp（不是规范 §2.2 写的 2dp）**。理由：
- 缝是**角度收缩**实现的，宽度 = `gapDp / pathRadius`。环路径半径 = (180dp − 26dp) / 2 = 77dp，
  所以 `gapDeg = gapDp / 77 × 180 / π`：1.5dp → **1.12°**，2dp → **1.49°**。
- 1.5dp 在 `density = 2`（多数中端机）上是 3px、`density = 3` 上是 4.5px，够抗锯齿；
  2dp 在 `density = 2` 上是 4px，缝会开始「看得出是一块空白」而不是「一条分隔」，
  在 180dp 的环上偏重，与「小狗风」轻量感冲突。
- 这是**规格层面的下调**，需在规范里同步改写（§2.2 与 §10.1 的 2dp 表述）。

> 若评审坚持 2dp：色值不变、对比度不变，只是 `DONUT_GAP` 常量从 1.5dp 改成 2dp，改动量 1 行。
> 这是**低代价可逆决定**，所以不在这里死磕。

**实现要点（决定 D7）**：
```kotlin
val gapDeg = DONUT_GAP.toPx() / pathRadiusPx * 180f / PI.toFloat()   // 1.5dp → 1.12°
val drawSweep = (sweep - gapDeg).coerceAtLeast(0f)
drawArc(
    color = color.copy(alpha = sliceAlpha),
    startAngle = startAngle + gapDeg / 2f,     // 缝居中，两侧各让一半
    sweepAngle = drawSweep,
    ...
)
```
- **不要**改成 `Stroke(cap = StrokeCap.Round)`：端帽只把扇区端头削圆，缝宽由**环宽（26dp）**隐含决定，
  无法指定 1.5dp，且会在环内外两侧各削掉半个环宽，视觉上像「珍珠项链」而不是「分隔缝」。
- **单分类边界情况**：`sweep = 360°` 时 `drawSweep = 360° − 1.12°`，会在 12 点方向留一道缺口。
  建议**特判**（`rows.size == 1` 时不收缩，单分类无相邻扇区、缝无意义），并在
  `CategoryDonutHitTest.kt` 加一条用例。
- 命中判定 `donutSliceAt`（`CategoryDonut.kt:112-141`）**不需要改**：它按未收缩的角度累加，
  缝上那 1.12° 会落进相邻扇区，手指点在缝上也命中——这正是想要的（缝太细，不该有「点了没反应」的死区）。

### 3.7 选中与未选中扇区的反馈（当前存在一处不达标，单列）

现状 `CategoryDonut.kt:229-230`：选中时其余扇区 `copy(alpha = DONUT_DIM_ALPHA)`（0.35）。
压暗后的实际色与对底色的对比：

| dim alpha | 浅色最差扇区对比 | 深色最差扇区对比 |
|-----------|------------------|------------------|
| **0.35（现状）** | **1.48**（`#42982D`→`#B6D8B6`） | **1.42**（`#AB5334`→`#452A22`） |
| 0.45 | 1.68 | 1.62 |
| 0.55 | 1.90 | 1.86 |

→ **无论取哪个 alpha，被压暗的扇区都到不了 3:1**，这是「压暗」这个手法本身的属性，不是取值问题。

**决定：不动 `DONUT_DIM_ALPHA`，记为「已知残留 + 非颜色补偿」**，理由：
- 被压暗的扇区此刻**不是当前操作对象**（用户已选中另一块），呈「非激活」状态是正确语义；
- 「哪一块被选中」有三重非颜色通道：其余扇区压暗（**相对明暗**变化，不是色相）、
  选中块环宽加大 `DONUT_SELECTED_STROKE_BONUS = 6dp`（`CategoryDonut.kt:237`，26dp → 32dp，**粗细**变化）、
  弹出的 `DonutTooltip`（分类名 + 金额 + 占比）。
- 备选（**若评审要求严格达标**）：未选中扇区改统一中性填充（浅 `onSurfaceVariant #41566A` → 7.24:1；
  深 `#BECEDA` → 11.51:1）。这是「不用颜色表达选中」的最强形式，代价是**失去「我选中的是这一块」的色相连续性**
  —— 点中「餐饮」后其他块全变灰，黄色消失，反而更难对应回排行条。**架构意见：不采纳备选**，数字列出由用户拍板。

## 10. ADR 摘要

**ADR-001：趋势柱改用图表专用色，不复用 `colorScheme.error/primary`**
- 背景：深色柱用中性灰，与「支出 = 红」语义冲突；直接复用 error/primary 会因角色错配导致观感失衡。
- 决策：新增 4 个填充专用色（浅 `#B9504B` / `#528AB9`，深 `#C05A52` / `#76A6D2`），经单一入口按主题下发。
- 备选：① 直接复用 error/primary（观感失衡、锚死文字角色）；② 用 `errorContainer/primaryContainer`
  （容器色过亮/过淡，对 surface 对比不达标）；③ 深色仍用中性灰、只改浅色（深色下语义依旧破）。
- 影响：语义护栏保住且图例/柱/折线三处必须同改；新增 `isSystemInDarkTheme()` 的隐性耦合（U4）。

**ADR-002：分类色从「排序位置」解耦为「分类身份」**
- 背景：`donutColorAt(index)` 使同一分类跨月跳色。
- 决策：`(categoryId × 7 + 3) mod 10` 取槽 + 同月确定性避让；图与条共用同一个 `categoryColors(rows)`。
- 备选：① 按分类名哈希（改名即换色、多语言跳色——否决）；② 保持按位置（跳色——否决）；
  ③ 按分类 ID 直接取模（相邻 ID 落相邻色相、区分度差——否决）。
- 影响：>10 个分类的月份存在有界漂移；换来跨月稳定。

**ADR-003：环缝保留，规格 1.5dp，由角度收缩实现**
- 背景：新板浅底最差 3.47:1 已达标，但相邻扇区之间的色相对比最低只有 1.02:1。
- 决策：保留背景色缝（缝与每块 3.47–5.09:1 ≥3:1），缝宽 1.5dp（1.12°），居中收缩扇区角度。
- 备选：① 不做缝、靠色相对比（1.02:1 不可行）；② `StrokeCap.Round` 端帽（缝宽不可控、形似项链）；
  ③ 缝用高对比灰（引入第三种「颜色」，增加编码噪声）。
- 影响：单分类月份需特判；规范 §2.2 的 2dp 表述需改写。

**ADR-004：选中格 overlay 保持 `primary.copy(alpha = 0.10f)`**
- 背景：规范 §10.1 / 清单 E-6 建议加到 0.14f。
- 决策：保持 0.10f。
- 备选：0.12f / 0.14f（浅色收入柱 2.92 / 2.83 <3:1，否决）；加深并单独调浅色收入柱色值
  （会破坏 §2.4 的亮度阶梯，连锁改动大，否决）。
- 影响：深色下选中态显著性偏弱，如需加强只加深色描边（U2）。

**ADR-005：分类色禁止用作文字/图标色**
- 背景：10 色对 surface 的对比上限只有 5.08:1、下限 3.47:1，都 <4.5:1 的正文门槛中的一部分。
- 决策：分类色只做填充；文字/图标一律 `onSurface` / `onSurfaceVariant` / `colorScheme.error`。
- 备选：为文字另做一套深色分类色（多 10 个色值、双份维护、与填充对不上号——否决）。
- 影响：占比条的金额文字继续是 `error` 红，与「分类色对号」是两个维度，需在规范里说清。
