## 2. 第 2 项：环形图 + 排行条共用一套蓝系分类色

### 2.1 核心决策（3 条，先看这个）

1. **一套「色位（slot）」体系，两套主题色值。**
   实测结论：**同一个 hex 不可能同时对 `#F5FAFF` 和 `#161E24` 都 ≥3:1** —— 对浅卡片要相对亮度 ≤0.252，对深卡片要 ≥0.258，两个区间**互斥**（数学结论，不是选择问题）。
   所以规范 §2.2 那句「不推荐为浅色单独做一套变暗的 10 色」**在「必须自带 3:1」这个前提下无法成立**，必须改为「同一套**色位排序** + 每主题一份色值」。
   跨主题一致性由**色相锚定**保证：同一 slot 在浅 / 深两套里是同一色相、同一 OKLCH 色度，只换明度。实测跨主题漂移 **最大 OKLab 距离 0.044**（阈值 0.06），人眼读作同一个颜色。
2. **深浅两套都自带 ≥3:1，不再靠 2dp 缝兜底。** 缝是**加强**，不是**合规依据**。
3. **分类 → 色位是「稳定哈希」，不是「金额排名」。** 见 §2.3。

### 2.3 分类 → 色位的稳定映射规则（**「同分类不跳色」的正式答案**）

**现状缺陷（E1）**：`CategoryDonut.kt:102` 是 `DONUT_COLORS[index % 10]`，而 `index` 来自 `ReportsScreen.kt:149-157` 的 `itemsIndexed(state.breakdown)`，即**按金额降序的名次**。
后果：同一个「餐饮」这个月排第 1（slot1），下个月排第 3（slot3），**颜色会跳**。这是必须修掉的真问题。

**推荐规则（稳定哈希，确定且可重放）**：

```kotlin
// CategoryPalette.kt（新增）
private const val CATEGORY_SLOTS = 10

/**
 * 分类 → 色位：按 categoryId 的稳定哈希取模。
 * 为什么不用「金额排名」当色位：排名每月变，同一分类会跳色（旧 donutColorAt(index) 的缺陷）。
 * 为什么不用「创建顺序」：分类可删可停用，序号会平移，同样会跳色。
 * 哈希对同一个 categoryId 永远给同一色位 → 跨月、跨页面、跨主题都不跳色。
 */
internal fun categorySlotFor(categoryId: Long): Int =
    ((categoryId.hashCode() % CATEGORY_SLOTS) + CATEGORY_SLOTS) % CATEGORY_SLOTS
```

**哈希碰撞怎么办（10 个位、通常 ≤8 个分类）**：同一张环形图里两个分类撞到同一 slot 是**可能的**（8 分类下约 2.4% 概率）。处理顺序：

1. **首选**：`resolveSlots(categoryIds)` 纯函数 —— 后来者沿色位序向后找第一个未被占用的 slot。这样**同一张图内部必定无重复**；只有发生碰撞时，被顶掉的那个分类的色位与它在别的月份可能不同（**只有碰撞时才这样，且规则确定**）。
2. 淘汰方案（不推荐，仅记录）：两套色板（`categoryId.hashCode() / 10 % 2` 选 A / B 板）能降低碰撞率，但视觉碎片化，且相邻扇区的区分度更难保证。

**排序如何保证同分类不跳色（正式回答）**：

- **绘制顺序仍按金额降序**（不动产品范围、不动 `StatsCalculator` 口径、排行条行序照旧），排名只决定**扇区从 12 点起的先后**（`CategoryDonut.kt:223-241`、`DONUT_START_ANGLE = -90f`）。
- **颜色不再跟排名走，跟 `categoryId` 走。**
- 排行条（`ReportsScreen.kt:149-157`）用同一个 `categorySlotFor(row.categoryId)`，所以「环形图上第 3 块」与「排行里第 3 行」**天然同色**，无需额外对齐逻辑。
- **并列名次的确定性**（防测试抖动）：规则写为 `ORDER BY amountCents DESC, categoryId ASC`。注意这是**绘制顺序**的 tie-break，不涉及 `StatsCalculator` 的口径（铁律 3 不受影响）。

### 2.4 是否保留 2dp 色缝？—— **保留，但降级为「增强」而非「合规依据」**

**结论：保留 2dp，缝色 = 主题 surface（不是 surfaceVariant，也不是卡片色）。**

理由（实算）：

- 缝必须同主题 surface 才能保证在任何卡片层级上都读得出；`surfaceVariant` 在浅色下是 `#DCE7F2`，与卡片 `#EFF6FD` 只差 1.15:1，做缝会看不清。
- 缝与每一段扇区的对比：浅色 `surface #F5FAFF` vs 各 slot = **3.41–4.32**；深色 `#0E1418` vs 各 slot = **4.69–5.76**。**全部 ≥3:1** —— 这就是「相邻对比替代色相对比」能成立的地方（WCAG 1.4.11 允许）。
- 新色板本身已自带 3:1（§2.2），即使缝在缩放 / 抗锯齿下被吃掉，扇区依然合规。**双保险**。

**缝的几何（必须与命中判定一致，否则点击会错块）**

- 环外径 180dp、环宽 26dp（`CategoryDonut.kt:43 / :46`）→ 描边中心线半径 = (180 − 26) / 2 = **77dp**（与 `CategoryDonut.kt:220-221` 的 `diameter = size.minDimension - strokePx` 一致）。
- 2dp 缝对应圆心角：`2 / 77 × (180 / π) = ` **1.49°**（**待复算**：真机必须按 px 算，公式 `seamDeg = seamPx / pathRadiusPx × 180 / π`）。
- 实现：`sweepAngle = sweep − seamDeg`，**`startAngle` 用原来的累计起点**（缝落在每段尾部）→ 缝宽恒为 2dp，短段也不会被扣成负数（短段按最小可见弧处理）。
- **必须抽公共函数**，让绘制与命中用同一套角度：

```kotlin
// CategoryDonut.kt 内新增（internal，供绘制与命中共用）

    rows.map { it.amountCents.toDouble() / totalCents * 360.0 }

```

命中判定 `donutSliceAt`（`CategoryDonut.kt:112-141`）**保持按未扣缝的角度累加**（:135-137 的 `swept += row.amountCents / total * 360`），所以**缝内的点击归属后一段** —— 这条要写进注释与测试，避免以后「修 bug」把它改坏。

## 4. 不确定项与代价（必须让用户看到）

1. **缝角度常量待真机复算**：`2dp / 77dp × 180 / π = 1.49°` 是按 dp 算的；实际要用 px（`DONUT_SEAM_DP.toPx() / pathRadiusPx`），并确认 1.5° 在 180dp 环上肉眼可见（约 2.7px @1.5x）。**标注为未验证**。
2. **排行条底槽 `surfaceVariant` 的 3:1 边界**：新板对底槽浅色 2.85–3.62、深色 2.31–2.84，一半 slot 略低于 3:1。**判定**：占比条是「填充 vs 同色系底槽」的**量级**表达，同行有百分比文字（`ReportsScreen.kt:414-418`）作主通道，颜色不是唯一通道。因此**不改底槽**，但在规范里标注为「已知、可接受」。若要求硬达标，代价是底槽改 `surfaceContainerHigh` 并重算（削弱「条」与「卡片」的分离感）。
3. **slot1 与浅色 primary 的色相重叠**（OKLab 距离 0.122）：可接受；若觉得「分类蓝」与「收入蓝」太像，把 slot1 色相挪到 195°（青碧侧）。
4. **哈希碰撞后「被顶掉」的分类跨月可能变色**：规则确定但非全局稳定。要 100% 全局稳定只能上两套色板或限制分类数，代价更大。**已知取舍**。
5. **深浅两套色值的代价（正是规范 §2.2 当初拒绝的那条）**：维护面从 10 个 hex 变成 20 个 hex，以后新增分类色要**成对**添加。这是为实现「两主题都自带 3:1」必须付的账 —— 而用户要的「深浅主题一致」是靠**色位排序 + 色相锚定**（跨主题漂移 ≤0.044）保住的，不是靠同一个 hex 保住的。这点要在评审时说清。
6. **本文档中的对比度全部为本机脚本实算**（WCAG 2.x 相对亮度、OKLab 用标准矩阵）；**未经真机截图取色复核**。落地后建议按 `LedgerPaletteTest` 的方式把数字固化成单元测试，而不是继续依赖文档。
